## Risk Register

1. **Fur-match algorithm tuning.** k-means lies when "background carpet" is the dominant cluster. **The Vanilla/Honey split (palette v1.1) means we MUST test these two as separate fixtures**, confusing them was the v1.0 failure mode that prompted the redesign. **Mitigation:** day 2 includes 22-fixture test suite (Vanilla cream Golden + Honey darker Golden as distinct cases) plus center-crop preprocess plus saturation floor. Cost: 0.5 day, saves 2 days of "why is Gabby Smoke" debugging on day 8.
2. **NativeWind 4 + pnpm + Metro setup.** Known minefield. **Mitigation:** day 1 must end with `bg-teal` rendering on real Android in Expo Go. If 4 hours of fighting, drop to NativeWind 2.
3. **shadcn neutral override leakage.** shadcn ships zinc/slate baked into every component. **Mitigation:** override CSS vars in `globals.css` on day 1 BEFORE generating any component. `/style-guide` route eyeball-checked daily.
4. **RLS lockout during seeding.** Service-role bypasses RLS only if `FORCE` is NOT set. **Mitigation:** never use `FORCE`. Test day 2 with anon key (must fail) and service-role (must succeed).
5. **Camera/image-picker permissions on Android (release APK).** MIUI/OneUI handle permissions weirdly. The demo phone runs the EAS release APK (not Expo Go), which simplifies things — no Expo Go SDK mismatch risk — but the OS-level permission prompts still vary by skin. **Mitigation:** install the release APK on the actual demo phone class by Day 8 rehearsal; grant camera + storage permissions during install; bundle 5 sample photos as in-app fallback if live camera fails on demo day.
6. **Conversion risk: Dr Sagar nods through the demo but doesn't commit** (the user's own biggest worry). **Mitigation:** the closing line is engineered to extract a verbal commitment, *"I'd like to come back next Tuesday with the role + comp plan. Same time?"* If he says "let me think," fallback script: *"Understood. Same time next Tuesday gives both of us a week. Deal?"* The two-step ask (today = vision, next-week = role/comp) means today's demo only needs to earn the right to come back, not close.
7. **Bilingual translation quality.** Auto-translated Marathi via DeepL/Google might read awkwardly to native ear. **Mitigation:** every translated string user-reviewed in the microcopy round; flag any that need a native Marathi speaker's edit before demo.
8. **Parent app fails low-literacy usability check at rehearsal.** The parent app must work for low-literacy users one-handed; if the rehearsal stand-in struggles, that's a real signal before demo day. **Mitigation:** pre-test the parent app with a stand-in low-literacy user during Day 8 rehearsal to catch the failure early and iterate before Sagar sees it. The actual demo audience is Jolene + Sagar only; no live low-literacy usability test happens during the demo itself.
9. **Video storage scale at real volume (v1+ concern, not v0).** v0 relies on `expo-image-picker`'s `videoQuality: '720p'` plus a 60s duration cap and a 50 MB soft size cap to keep parent-uploaded videos within the Supabase free tier (1 GB). At ~5-15 MB per video this comfortably covers the demo and early ops (~65-200 videos). At real Pawkit volume across multiple clinics, this approach will hit the storage ceiling and slow uploads on weak connections. **Mitigation (v1+):** server-side compression via Supabase Edge Function (upload original to a temp bucket, re-encode to target bitrate, move compressed copy to permanent bucket, delete original). Decoupled from client; benefits all uploads regardless of source. Deferred from v0 because Edge Function setup adds complexity and the size-cap-plus-720p approach is sufficient for demo and early adoption. **Trigger to revisit:** when Pawkit Supabase storage usage crosses ~70% of paid tier OR when parent uploads exceed 500/month per clinic.
